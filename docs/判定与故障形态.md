# 体检判定与故障形态

> 本文说明 NetDoctor 的**判定引擎**：它先回答「当前网络是否正常」，
> 再判定属于哪种**故障形态**，并按形态给出**分别处理**的修复预案。
>
> 实现位置：`netdoctor/diagnose.py`（判定逻辑）、`netdoctor/probes.py`（分层探针）、
> `netdoctor/scanner.py::_verdict_with_hints`（提示级归并）。

## 一、为什么需要判定

同类工具的通病是「只要有可疑项就一股脑列出来」。结果是：网络明明是好的，
用户却被十几条「疑似原因」吓到——其中还混着 `hosts 文件存在自定义记录`、`检测到 Windows Defender`
这类根本不影响上网的噪声，于是只好全部点一遍「修复」，反而把好配置改坏。

判定引擎解决三件事：

1. **先给结论**：网络是否正常、断在哪一环；
2. **说清范围**：哪些功能还能用、哪些已经不能用；
3. **分别处理**：不同形态走不同的修复预案，不做与故障无关的操作。

## 二、判定原则（v1.2.0 起）

> **健康度只由实测连通性决定。**

- 探针证明**能实际上网** → 判为「网络健康」（绿色）；
- 实测不通 → 才按「断在哪一层」落到「能连网但上网受限」或「完全断网」。

对应地，**配置类检出**——hosts 自定义记录、静态 IP、PAC 脚本、系统代理设置、
代理环境变量、Winsock 条目偏多、虚拟网卡、网卡节能、多条默认路由等——只要实测能上网，
就**一律不压低健康度**，统一以**「提示」级**列出（仍然完整展示、仍给处理方案）。

理由很直接：这类项多半是**用户自己的设置**（例如主动写 hosts 屏蔽广告、为开发环境设定的
代理环境变量）或**无害残留**。既然实测上网正常，就说明它们当前没造成问题，
不该被报成故障、更不该被「一键修复」改掉。

只有**探针直接测到**的缺陷才升级健康度：

| 实测缺陷 | 依据 | 结果 |
|---|---|---|
| 各层连通性失败 | 分层探针 | 受限 / 全断 |
| MTU 分片黑洞 | `ping -f` 二分查找最大可用 MTU ≤ 1300 | 能连网但上网受限 |
| 系统时间偏差 | HTTP 响应头服务器时间 vs 本机时间 > 300 秒 | 能连网但上网受限 |

## 三、健康度档位

| 档位 | 代号 | 含义 | 界面表现 |
|---|---|---|---|
| 网络健康 | `normal` | 实测可以正常上网 | 绿色横幅；不弹窗、不勾选任何修复项；配置类检出列为「提示」 |
| 能连网，但上网受限 | `limited` | 底层连通，但某个环节（域名/端口/代理/MTU/时间）导致部分功能不可用 | 橙色横幅 + 勾选该形态的修复预案 |
| 完全断网 | `down` | 应用层完全不可达 | 红色横幅，并提示可能需要联系专业人员 |
| ~~可以上网，但有隐患~~ | `risk` | **保留档位**：留给日后「在线但被测到局部能力受损」的场景 | 当前判定逻辑下不会产生 |

## 四、判定顺序（命中即归类）

```
① 本机协议栈(127.0.0.1) 不通 ─┐
② 默认网关不可达             ├─→ 完全断网（stack / lan / wan）
③ 公网 IP 不可达             ┘
④ 公网可 ping 通，但域名解析失败 ─→ 能上QQ打不开网页（dns）
⑤ 域名可解析、TCP 443 与 HTTP 均失败 ─→ 端口被阻断（port）
⑥ TCP 443 通、HTTP 取不到内容 ─→ 应用层异常（app）
⑦ 直连全通、唯独经系统代理不通 ─→ 只有浏览器上不了网（proxy-broken）
⑧ 以上全通 → 只看「实测缺陷」：time-skew / mtu；其余配置类检出统一降为「提示」
⑨ 连通性判定口径：「应用层是否能通」= TCP 443 通 **或** HTTP 通
```

其中第 ⑦ 步依赖专门的**浏览器路径探针**，见第七节。

## 五、故障形态与处理预案

「修复动作」列即该形态下默认勾选的动作（取自 `fixids.py`），左侧为优先顺序。

| 形态代号 | 形态名称 | 健康度 | 判定条件 | 修复动作（按优先级） |
|---|---|---|---|---|
| `stack` | 本机协议栈异常 | 全断 | 127.0.0.1 不通且应用层不可达 | `tcpip.reset`(进阶) → `winsock.reset`(进阶) → `adapter.restart` |
| `lan` | 局域网不通 | 全断 | 网关与公网均不可达 | `dhcp.renew` → `adapter.restart` → `route.refresh` |
| `wan` | 外网出口不通 | 全断 | 网关通、公网不可达 | `dhcp.renew` → `route.refresh` |
| `dns` | 域名解析故障（能上QQ打不开网页） | 受限 | 公网可 ping 通、域名解析失败 | `dns.flush` → `dns.setpublic` → `hosts.restore` → `dhcp.auto` |
| `port` | 端口/协议被阻断 | 受限 | 公网与解析均通，TCP 443 与 HTTP 都失败 | `proxy.disable` → `proxy.env` →（进阶）`firewall.reset` |
| `app` | 应用层访问异常 | 受限 | 443 建连成功、HTTP 拿不到内容 | `proxy.disable` → `proxy.env` → `dns.flush` |
| `proxy-broken` | 浏览器路径被代理堵死 | 受限 | 直连全通、经系统代理访问失败 | `proxy.disable` → `proxy.env` |
| `mtu` | 大包被丢弃（MTU 异常） | 受限 | 各层通，但最大可用 MTU ≤ 1300 | `mtu.reset` |
| `time-skew` | 系统时间偏差 | 受限 | 与网络时间偏差 > 300 秒 | `time.sync` |
| `normal` | 网络健康 | 健康 | 各层全通、无实测缺陷 | 不勾选任何项 |

> 标注「进阶」的动作属 `FixMode.ADVANCED`，不会被自动勾选，需用户二次确认，且通常需要重启。

**修复项挑选规则**：`形态预案 ∩ 本次实际检出` → 若一个都没检出，则回落到该预案最安全的前两项，
让用户可按需勾选。因此「网络健康」时默认**不勾选任何项**。

## 六、提示级条目（原「隐患」的归处）

网络实测正常时，扫描出的配置类条目全部以**「提示」级**呈现：

- 仍完整列出（GUI 列表里排在最后；CLI 单独一节「其他提示」）；
- 仍给出问题说明与处理方案（GUI 点该行即可看到「手动修复指引」/「自动修复」）；
- **不计入**「需处理 N 项」，**不自动勾选**，健康度不受影响。

典型条目：

| 条目 | 为什么只提示 |
|---|---|
| `C.hosts` hosts 文件存在自定义解析记录 | 很可能是用户主动添加的（屏蔽广告、加速访问）；实测能上网即说明未造成影响。**断网时**会正常参与判定 |
| `E.system-proxy` / `E.pac` / `E.env-proxy` | 可能是有意配置的代理；代理真失效时会被**浏览器路径探针**直接测出来，判为 `proxy-broken`（受限），不会只当提示 |
| `B.static` 使用静态 IP | 内网固定 IP 是常见的有意配置 |
| `D.winsock` Winsock 条目偏多 | 过滤驱动残留，实测正常即未造成影响 |
| `I.powersave` 网卡节能 | 只有在真的出现「挂机掉线」时才算故障 |
| `G.multi-default` 多条默认路由 | 同上；若真的抢占了路由，会导致实测不通 |

**断网时**（实测不通）这些条目不再降级，按原有严重度参与「疑似原因」清单——
例如 DNS 故障时 `C.hosts` 会被列为高危嫌疑项，`dns` 预案里也包含 `hosts.restore`。

## 七、浏览器路径探针（区分「只有浏览器上不去」与「全断」）

关键探针：`probes.py::probe_via_system_proxy`。

**原理**：浏览器只认**系统代理**（WinINET，注册表 `HKCU\...\Internet Settings` 的
`ProxyEnable` / `ProxyServer`），而微信、QQ、网游等程序走直连；命令行工具读的是
`HTTP_PROXY` 环境变量——三者互不相同。

**做法**：读注册表拿到浏览器真正在用的代理地址，用 `urllib` 显式经该代理访问测试站点：

- 直连探针（`probe_http`，显式禁用代理）**通**，而经代理**不通** → 判定 `proxy-broken`；
- 同时产出一条扫描发现项 `E.browser-path`（级别：高，可直接一键关闭代理修复）。

这样就能把几种截然不同的故障分清楚：

| 现象 | 探针表现 | 判定 |
|---|---|---|
| 微信/QQ 正常，浏览器打不开网页，但 ping 得通 IP | 直连通、经代理不通 | `proxy-broken`（浏览器路径被代理堵死） |
| 微信/QQ 正常，浏览器打不开网页，ping IP 通但域名不解析 | 公网通、`DNS解析` 失败 | `dns`（域名解析故障） |
| 什么都上不去 | 网关/公网/应用层全断 | `lan` / `wan` / `stack`（完全断网） |

## 八、与其他模块的关系

```
probes.run_quick()   ──→ diagnose.judge()  ──→ 界面横幅（秒级先给结论）
        │                      ↑
        └→ run_all() ──→ scanner 十类检查 ──→ findings ──┘
                                                     │
                              _verdict_with_hints() ─┤ 实测正常 → 配置类检出降为「提示」
                                                     │
                                                     ├─→ 界面列表 + 详情区（不弹窗）
                                                     │
                                          flow.execute() 备份 → 修复 → 复测
                                                     │
                                     仍未连通 → diagnose.explain_unfixed() 按形态给下一步
```

- **快检**（`scanner.quick_check`）：只跑定性探针，几秒出判定，GUI 开屏即用、CLI `--quick`；
- **完整扫描**（`scanner.scan`）：跑全量检查，用带 findings 的判定决定默认勾选项，
  并按第二节的原则把配置类检出降为「提示」；
- **修复后仍不通**：`explain_unfixed()` 按形态给出下一步（如 `dns/app/port` 类提示换设备对比、
  `stack/lan/wan` 类直接建议联系运营商并提供诊断报告）。

## 九、误报与打扰控制

| 问题 | 处理 |
|---|---|
| 网络健康时报出十几条「疑似原因」 | 配置类检出统一降为「提示」级，不计入「需处理」 |
| 网络健康时弹窗打扰 | GUI **不使用结果类弹窗**，判定/修复/回滚结果全部在界面内呈现 |
| `hosts` 是用户自己写的却被报成故障 | 实测正常时降为提示；断网时才作为嫌疑项 |
| Windows Defender 被当作「第三方安全软件」 | 过滤 `Defender / Microsoft Security`，仅报真正的第三方安全软件 |
| 无无线网卡时仍报 WLAN 设备残留 | 「Not Present」设备不再计入可用网卡，仅当**所有**网卡都不可见时才提示 |
