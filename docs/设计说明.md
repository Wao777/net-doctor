# 设计说明

## 一、设计目标与约束

| 目标 | 落地方式 |
|---|---|
| 能打包发布，任意 Windows 机器免环境运行 | PyInstaller 单文件/文件夹双输出，自带 Python 与 Tcl/Tk 运行时 |
| 自动遍历可能导致断网的原因 | 10 大类检查 + 分层连通性探针（含浏览器路径实测），覆盖到"具体哪一层断了" |
| 疑似原因全部列出并给方案 | `Finding` 统一模型：标题 + 说明 + 证据 + 手动指引 + 可自动修复标记 |
| 结果不打扰用户 | 健康度只由实测连通性决定；实测正常时配置类条目降为「提示」级；GUI 不使用结果类弹窗 |
| 修复前先备份 | `BackupManager` 强制落盘，`manifest.json` 记录还原方式 |
| 修复后监测连通性 | 修复完成后重新执行完整扫描（含探针），与修复前结论做集合比对 |
| 修不好要能说清"该找谁" | `_make_verdict()` 区分「问题已修好但仍不通」与「问题没修好」两种语义 |

**关键约束：**

- 只支持 Windows；不引入任何第三方运行时依赖（GUI 用标准库 tkinter）。
- 扫描阶段绝对只读，任何写操作必须发生在用户确认之后。
- 不调用 `reg.exe` / `sc.exe`：这两者常被安全策略或安全软件限制，改用 winreg API 与 WMI/PowerShell。

## 二、模块分层

```
                 ┌──────────────┐        ┌──────────────┐
   界面层        │   gui.py     │        │   cli.py     │
                 └──────┬───────┘        └──────┬───────┘
                        └────────┬──────────────┘
                                 ↓
                 ┌───────────────────────────────┐
   编排层        │           flow.py             │  扫描→备份→修复→复测→结论
                 └──────┬─────────────┬──────────┘
                        ↓             ↓
        ┌───────────────┴──┐   ┌──────┴─────────────┐
   能力层│ scanner.py       │   │ backup.py          │
        │ probes.py        │   │ fixers.py          │
        │ report.py        │   └────────────────────┘
        └───────┬──────────┘            ↑
                ↓                       │
        ┌───────┴──────────┐   ┌────────┴───────────┐
   基础层│ netstate.py     │   │ util.py            │ 命令/权限/日志/注册表
        │ models.py       │   │ fixids.py          │ 常量表
        └────────────────┘   └────────────────────┘
```

各模块职责：

| 模块 | 职责 | 关键接口 |
|---|---|---|
| `util.py` | 命令执行（超时/编码兼容/隐藏窗口）、管理员检测与自提权、日志、注册表读写与导入导出、服务查询与设置 | `run()` `is_admin()` `reg_export_key()` `query_services()` |
| `models.py` | 数据模型：`Finding` `FixAction` `FixOutcome` `ProbeResult` `ScanReport` `Verdict` `HealthLevel` | `ScanReport.suspicious` `ScanReport.concerning` `ScanReport.online` `ScanReport.healthy` |
| `fixids.py` | 修复动作 id 常量、关键服务名单、公共 DNS 列表 | `FIX_*` 常量 |
| `netstate.py` | 网络状态结构化采集（PowerShell NetTCPIP 优先，netsh 降级） | `collect() -> NetState` |
| `probes.py` | 分层探针：含 `run_quick()`（秒级体检）与 `probe_via_system_proxy()`（浏览器路径实测） | `run_all()` `run_quick() -> List[ProbeResult]` |
| `diagnose.py` | **判定引擎**：健康度（健康/受限/全断）+ 9 种故障形态 + 分形态修复预案 + 提示级归并 | `judge() -> Verdict` `explain_unfixed()` |
| `scanner.py` | A~J 十类检查，产出 `Finding`；汇总后调用判定引擎（`_verdict_with_hints()` 负责按实测结果归并提示级） | `scan() -> ScanReport` `quick_check() -> ScanReport` |
| `backup.py` | 备份、manifest、回滚 | `BackupManager.backup_all()` `BackupManager.restore()` |
| `fixers.py` | 17 个修复动作实现与调度 | `run_fix()` `run_fixes()` `ACTIONS` |
| `flow.py` | 编排：计划 → 备份 → 修复 → 复测 → 结论 | `plan_fixes()` `execute() -> FlowResult` |
| `report.py` | 文本与 HTML 报告（含判定结论卡片） | `save() -> (txt, html)` |
| `gui.py` / `cli.py` | 两个前端（健康度横幅 + 界面内呈现结果 / `--quick`） | `run()` / `main(argv)` |
| `main.py` | 入口分流：有参数走 CLI，无参数走 GUI | `main()` |

## 三、核心数据流

```
netstate.collect()  ──►  NetState（网卡/IP/DNS/路由）
                              │
probes.run_all()    ──►  List[ProbeResult]（分层连通性）
                              │
                              ▼
scanner.scan()      ──►  ScanReport（findings + probes + info）
                              │
                    flow.plan_fixes()  挑出可自动修复项（按动作去重）
                              │
                              ▼
                    BackupManager.backup_all()   强制备份
                              │
                    fixers.run_fixes()           执行修复
                              │
                    scanner.scan()               复测（重新完整扫描）
                              │
                    _make_verdict()              结论判定
                              ▼
                    FlowResult（outcomes + verdict + need_professional）
```

## 四、关键设计决策

### 1. 为什么用「扫描器 / 修复器」分离而不是边扫边修

断网场景下用户最需要的是**先看清全貌**再决定做什么。分离后：
- 扫描可以独立运行（`--scan`），零风险；
- 修复项可以按用户勾选精确执行；
- 复测可以复用同一套扫描逻辑，前后结论可直接做集合比对。

### 2. 结论判定为什么要区分两种「失败」

`flow._make_verdict()` 是需求里最容易被忽略、但实际最关键的一段：

```
复测仍不通
├── 已勾选的问题项在复测中全部消失 → 「问题已修好但仍不通」
│      → 故障不在本机配置层（线路/光猫/路由器/硬件/准入认证）
│      → need_professional = True，提示联系专业人员或运营商
└── 仍有问题项存在 → 「问题没修好」
       → 列出未修复项 + 执行失败的动作用 + 手动指引
       → 若含高危项或需重启，也提示需进一步处理
```

这段逻辑直接对应需求里的"若问题已修复仍是断网，提醒用户需联系专业人员判断"。
v1.1.0 起，这条兜底文案还会按**故障形态**（`diagnose.explain_unfixed()`）细化：
`stack/lan/wan` 类直接指向硬件与线路并建议报修；`dns/app/port/proxy-broken` 类
则建议先「换设备对比」以区分本机问题与网络侧问题。

### 2.1 判定引擎：先判「是否正常」，再按形态分别处理

原有实现只有一个 `online` 布尔值，且只要检出可疑项就全量展示，导致**网络正常时也在
报噪声**（例如：网络全通却列出 hosts 自定义记录、代理环境变量、WLAN 设备残留，
连 Windows Defender 都被当成第三方安全软件）。v1.1.0 引入 `diagnose.judge()`：

```
probes（分层探针）
   ├─ 应用层是否可达（TCP 443 通 或 HTTP 通）
   ├─ 域名能否解析
   └─ 浏览器路径是否通（按系统代理实测）
        ↓
HealthLevel（健康 / 受限 / 全断）        ← 只由「实测连通性」决定
        ↓
fault（9 种形态之一）
        ↓
Verdict{ 影响面, 处理步骤, fix_ids }  ← fix_ids = 形态预案 ∩ 实际检出
```

四个关键设计：

1. **应用层可达才叫「能上网」**：`online` 不再由「ping 通公网」决定，而是由
   TCP 443 / HTTP 是否成功决定——否则「DNS 全挂」的机器会被判成正常。
2. **浏览器路径单独实测**：浏览器只认系统代理（注册表 WinINET），命令行工具读
   `HTTP_PROXY` 环境变量，两者互不相干。因此用「按注册表代理访问测试站点」来
   判定「只有浏览器上不去」（详见《判定与故障形态》第七节）。
3. **修复项由形态反查**：`fix_ids = 形态预案 ∩ 本次检出`，取不到时回落该预案最安全的
   前两项。网络健康 → `fix_ids` 为空 → 界面不勾选任何项，从机制上避免「好配置被改坏」。
4. **健康度只由实测决定（v1.2.0）**：配置类检出不再压低健康度。
   `scanner._verdict_with_hints()` 先判一次，若 `verdict.online` 为真且健康度优于「受限」，
   就把除 `G.mtu` / `I.time-skew`（探针实测到的真实缺陷）与 `J.*`（连通性结论）之外的
   finding 统一改为 `Severity.INFO`，再判第二次，让提示清单进入结论文案。
   两趟都是纯计算（无 I/O），代价可忽略。
   这样做是因为：hosts 记录、静态 IP、代理设置、节能等**可能是用户自己的设置**，
   实测能上网就说明没造成问题——既不该报警，更不该被「一键修复」改掉。

安全约束：`_filter_fix_ids()` 会把 `FixMode.ADVANCED` 与 `default_selected=False`
的动作剔除，因此进阶动作永远不会被自动勾选。

### 3. 误报控制与打扰控制

初版实现会把「按需启动的服务已停止」「设备记录存在但硬件不可见」都报成高危，实际这些在正常机器上也大量存在。
现在的策略：

- 服务检查区分**常驻服务**（Dhcp/Dnscache/nsi/RpcSs，停止即异常）与**按需服务**（Netman/NlaSvc/netprofm/WlanSvc）；
- 按需服务只在 `env.online == False`（当前确实断网）时才提示，网络正常时不打扰；
- `Not Present` 的设备记录**不再计入可用网卡**（`Env.real_adapters` 过滤），仅当所有网卡都不可见时才提示；
- Windows Defender / Microsoft Security 不再被当作「第三方安全软件」；
- `C.hosts` 在实测正常时直接判为 `Severity.INFO`（断网时仍按原严重度参与判定）；
- `ScanReport.concerning` 只统计 `severe <= 中` 的项，「提示」级归入「其他提示」，
  网络正常时界面不把它们当作待处理问题；
- **GUI 不使用结果类弹窗**：判定/修复/回滚/报错统一走 `_show_notice()` 显示到详情区 +
  状态条；只保留 3 个会改动系统的「确认」对话框。

`env.online` 由探针结果在检查开始前回填——这要求 `scanner.scan()` 里探针必须先于检查执行；
且 `--fast` 模式下 TCP 443 / HTTP 两个探针**必须保留**（它们是判定「只剩浏览器上不去」的依据）。

### 4. 备份的粒度和回滚能力

| 类型 | 例子 | 回滚方式 |
|---|---|---|
| 可无损回滚 | hosts、注册表代理键、服务启动类型 | 直接写回 |
| 只读存档 | ipconfig /all、路由表、MTU、防火墙配置、Winsock 目录 | 供人工比对，不做自动回写 |

注册表备份刻意不用 `reg export`，而是用 `winreg` 递归导出为 JSON（含值类型），
回滚时逐值写回。好处：不依赖 `reg.exe`（常被限制），且导入粒度更可控。

### 5. GUI 线程模型

tkinter 不是线程安全的。所有耗时操作（扫描、修复、回滚）都在后台线程执行，
通过 `queue.Queue` 把日志与结果事件回传，主线程用 `after(120ms)` 轮询消费。
界面上「正在扫描…」的进度、日志滚动、按钮禁用状态都由这套机制驱动。

### 6. 单 exe 同时支持 GUI 与 CLI

PyInstaller 打 `--console` 版（CLI 需要控制台才能输出），
图形模式启动时调用 `gui.hide_console()` 通过 `GetConsoleWindow + ShowWindow(SW_HIDE)` 隐藏控制台。
这样避免发布两个 exe，也避免 `--noconsole` 版让 CLI 输出丢失。

### 7. 控制台编码

PyInstaller 产物会忽略 `PYTHONUTF8` / `PYTHONIOENCODING` 环境变量，
在 MSYS/Git Bash 这类 UTF-8 终端下中文会输出成 GBK 字节而乱码。
`cli._configure_output()` 据此决定：终端是 UTF-8 或输出被重定向 → 切 UTF-8；
原生 Windows 控制台（GBK 代码页）→ 保持系统编码。

## 五、扩展方式

### 新增一个检查项

1. 在 `scanner.py` 对应 `check_*` 函数里追加一段逻辑，构造 `Finding`；
2. 若该项可自动修复，在 `fixids.py` 里加动作 id 常量，并在 `fixers.py` 里用 `@action` 装饰器注册实现；
3. 在 `docs/扫描与修复项清单.md` 补一行。

### 新增一个修复动作

```python
@action(F.FIX_XXX, "动作名称", "动作说明（会显示给用户）",
        mode=FixMode.SAFE, needs_reboot=False, default_selected=True)
def fix_xxx(ctx: FixContext) -> FixOutcome:
    guard = _guard()                      # 管理员权限检查
    if guard:
        return guard
    ctx.backup.backup_xxx()               # 先备份
    ok, msg, cmd = _exec(ctx, [...], label="…")
    return FixOutcome(F.FIX_XXX, "动作名称", ok, msg, [cmd])
```

`mode=FixMode.ADVANCED` 的动作默认不勾选，GUI 会弹二次确认；
`default_selected=False` 的动作需要用户手动勾选。

### 新增一类探针

在 `probes.py` 里加函数，然后在 `run_all()` 的 `step(...)` 序列里插入；
若希望它参与 J 类结论推导，在 `scanner._J_LAYERS` 里补一层。
